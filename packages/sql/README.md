# @simtlix/simfinity-sql

Driver-free relational planning, record reconstruction, and transaction orchestration for Simfinity. It requires Node.js 18.18 or later and GraphQL 16. It depends only on `@simtlix/simfinity-core`; it does not install `pg`, MongoDB, Mongoose, MCP, or a database plugin.

PostgreSQL 15 or later is the first and only supported SQL plugin. Install the SQL runtime and PostgreSQL plugin at matching versions:

```sh
npm install @simtlix/simfinity-sql@3.15.0 @simtlix/simfinity-postgres@3.15.0 graphql@^16.11.0 pg@^8.16.3
```

## Runtime

```javascript
import pg from 'pg';
import { createSQL } from '@simtlix/simfinity-sql';
import { postgresPlugin } from '@simtlix/simfinity-postgres';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const simfinity = createSQL({ plugin: postgresPlugin({ pool, schema: 'library' }) });

simfinity.connect(null, BookType, 'book', 'books', bookController);
const schema = simfinity.createSchema();
await simfinity.initializeDatabase({ mode: 'create' });

// Serve schema. The application owns the pool and calls pool.end() at shutdown.
```

`createPostgres({ pool, schema })` remains a convenience factory for this same implementation. Both entry points preserve PostgreSQL descriptions, generated SQL, GraphQL operations, scopes, hooks, state machines, model handles, and session behavior. The [PostgreSQL package guide](https://github.com/simtlix/simfinity.js/tree/master/packages/postgres) describes the supported storage and query shapes.

A runtime permanently binds one plugin and configuration. Its methods and capabilities are captured at creation; connection objects remain caller-owned. To configure later, use `createSQL({ plugin: postgresPlugin() })`, then call `configure({ pool, schema })` once before `createSchema()`. Register all types before creating the schema and await successful initialization before serving operations. Give each runtime its own GraphQL type objects: a type whose relation resolvers one runtime generated, a `toConfig()` copy of it made afterwards, or a shared custom mutation result type with an unresolved relation field throws `TYPE_BOUND_TO_OTHER_RUNTIME` in another.

`initializeDatabase({ mode: 'create' })` creates missing compatible storage; `mode: 'validate'` validates existing storage. Incompatible definitions are rejected. `preventCreatingCollection(true)` forces validation: a missing or false mode validates, and every other mode except `validate` fails with `DATABASE_CREATION_DISABLED` (409). On a runtime that allows creation, any mode other than `create`, `validate` or an omitted one, including `null` and `''`, fails with `INVALID_INITIALIZATION_MODE` (400). Both are rejected before the plugin is called. PostgreSQL initialization performs no destructive migration or schema synchronization.

Operations fail with `DATABASE_NOT_INITIALIZED` (503) until the first initialization succeeds. A rejected request leaves readiness as it was, a ready runtime keeps serving while it is initialized again, and any failure of the initialization started last makes storage unavailable until a later one succeeds. Check a live runtime with `mode: 'validate'`: when PostgreSQL's `create` mode creates objects, writers of the tables that it changes, of existing tables that a new foreign key references, or of roots whose keys it rebuilds wait until it commits. It locks no table when nothing is missing.

The runtime exposes the core registration and GraphQL lifecycle APIs, `configure`, `describeDatabase`, `compileDatabaseSchema` (the plugin's DDL for this runtime's schema, for review or export; it does not touch storage), `initializeDatabase`, `withTransaction`, and shared `auth`, `plugins`, `scalars`, and `validators` helpers. Model handles expose `findById`, `find`, `create`, `update`, and `delete`. `find(args, { session })` accepts the generated list query's filters, sorting, and pagination. Native model helpers bypass GraphQL controllers and validators and use storage field names.

`withTransaction(session, callback)` joins an active session belonging to this runtime, or owns a new transaction when no session is supplied. Sessions expose `client`, `query(text, values)`, and `inTransaction()`. PostgreSQL uses repeatable-read isolation and retries confirmed serialization/deadlock aborts up to five times, each after a random delay of less than 10, 20, 40, 80 and 160 ms. Without a session, a read that one statement answers runs on one connection without a transaction when the plugin advertises `singleStatementReads`, as PostgreSQL does. Owned rows are inserted with multi-row statements when the plugin supports them, unless the configuration sets `multiRowInserts: false`. Unknown commit outcomes are not replayed, and the application-owned pool stays open. Named views need no session: they run the generated list path. Custom queries registered with `registerCustomQuery()` receive no session; a callback that needs a transaction calls `withTransaction(null, callback)`.

Types declaring `extensions: { concurrency: { mode: 'optimistic' } }` receive a managed `version` field. Protected model handles create records at version 1, require `model.update(id, { ...changes, version: record.version }, { session })` and `model.delete(id, { session, version: record.version })`, and return `VERSION_CONFLICT` (409) for stale versions. Updates advance the version even when no data fields change; at `MAX_RECORD_VERSION` they fail with `VERSION_EXHAUSTED` (409), while deletion remains possible. The handle captures the supplied version once before transaction retries and does not mutate the caller's changes. A missing version gets `REQUIRED_VALUE` (400) with guidance for this handle. For a derived value maintained by a hook in the same transaction, `model.update(id, changes, { session, version: false })` preserves the stored version and ignores `changes.version`; deletion also accepts `version: false`. These native helpers still bypass validators, controllers, scopes and authorization. Handles for unprotected types keep their existing behavior and ignore the version option. `RecordVersion` and `MAX_RECORD_VERSION` are re-exported from core.

## Relational planning

```javascript
import { describeModels } from '@simtlix/simfinity-core';
import { planRelationalSchema } from '@simtlix/simfinity-sql';

const models = describeModels([{ gqltype: BookType }]);
const plan = planRelationalSchema(models, { schema: 'library' });
```

`planRelationalSchema(models, { schema, naming })` is pure: it returns serializable logical tables, scalar columns, foreign keys, indexes, checks, owned-record metadata, and `requirements`. Logical columns have `scalar`, `list`, and `nullable` properties. They contain no physical SQL types, SQL expressions, or driver objects. An optional `naming` object provides `validateIdentifier(value)` and `generatedName(...parts)` to enforce engine naming limits.

Protected types add a required logical `Version` column with default 1 and the `optimisticConcurrency` requirement. The plugin must declare that capability or preparation fails with `UNSUPPORTED_SQL_CAPABILITY`. The SQL adapter declares `writeFeatures.optimisticConcurrency` to core; the plugin implements the atomic storage operation.

## Plugin contract, version 1

A plugin factory returns an object with `apiVersion: 1`, `name`, `displayName`, `defaultSchema`, configuration `options` or `null`, a `capabilities` array, an optional `queryFeatures` declaration, and these members:

| Member | Responsibility |
| --- | --- |
| `naming` | Validate identifiers and generate engine-compatible names. |
| `describeSchema(plan, configuration)` | Lower the logical plan into physical storage metadata. Receives the bound configuration, or `null`, as its last argument. |
| `compileSchema(description)` | Return reviewable DDL statements. The runtime calls it only from `compileDatabaseSchema()`. |
| `initialize(configuration, description, options, context)` | Create or validate storage and return `{ mode, created }`. Receives only `create`, `validate` or no mode, and must keep accepting indexes that earlier versions generated on its databases, such as the `[ID]` list index. Only when the runtime's types declare virtual fields does it receive `context`, `{ virtualFields }`: where each one would hold storage (`{ table, path, field, name }`), so that a schema mismatch can name a field whose storage from before it became virtual is still in the database. |
| `compileQuery(models, description, queryPlan, extra, configuration)` | Return `{ text, values, aggregateFields? }`. Aggregate queries include the group field followed by each fact field in `aggregateFields`. Receives the bound configuration, or `null`, as its last argument. |
| `compileChildrenQuery(models, description, queryPlan, { column, ids }, configuration)` | Optional; used only with `batchedCollections: true`. Return `{ text, values, parentColumn, setup? }`: one statement whose rows, for each parent in `ids`, are exactly the rows `compileQuery` returns for `{ column, id }`, in the same order, each with its parent's 1-based position in `ids` under `parentColumn`. The optional `setup`, which may also be `null`, lists statements (`{ text, values? }`) that run, in order, on the same connection right before it, such as transaction-scoped settings; their rows are ignored. Receives only paginated find plans and 1 to 100 distinct cast IDs. |
| `compileRecord(description, operation)` | Compile one record operation into `{ text, values }`. |
| `compileRecordBatch(description, operation)` | Optional, with `maxRecordBatchValues`. Compile `{ kind: 'insertMany', table, rows }` (`SQLInsertManyOperation`) into one statement that inserts every row; the rows share their columns in the same order and no result rows are needed. A single row goes through `compileRecord`. |
| `maxRecordBatchValues` | Optional, with `compileRecordBatch`. A positive safe integer: the most values, rows times columns, of one batch statement. |
| `values` | Create/cast IDs, encode/decode scalars, and encode embedded values. |
| `driver` | Validate configuration, execute statements, acquire/release clients, begin/commit/rollback transactions, classify retryable aborts, and normalize errors. |

The driver supplies `assertConfiguration`, `query`, `acquire`, `begin`, `commit`, `rollback`, `release`, `isRetryable`, and `normalizeError`. `query(configuration, statement, client?)` returns a promise resolving to `{ rows, rowCount? }`; `client` is the connection of a transaction or of a single-statement read, and counts and aggregates omit it. `release(client, error?)` receives the rollback failure when ROLLBACK did not complete, including the probe after a failed single-statement read; the driver must then discard the connection instead of returning it to a pool, and SQL does not retry that attempt. For an error that `isRetryable` accepts, SQL waits its retry delay only after `release` has completed, so the failed attempt holds no connection meanwhile. A single-statement read runs `acquire`, `query` and `release` without `begin` or `commit`; SQL retries it for an error that `isRetryable` accepts, with the same delays and limit, without a rollback step. After any other failed driver call it calls `rollback(client)` outside a transaction to probe the connection; an error raised before any statement, such as `NOT_VALID_ID`, releases the connection without a probe and passes a probe failure to `release(client, error)`, so `rollback` must resolve on a usable connection with no open transaction and reject on an unusable one; the read's own error is reported. A transaction session stops accepting statements as soon as its callback settles, before COMMIT or ROLLBACK is sent, so un-awaited session work fails with `INVALID_SESSION`. `commit(client)` must reject when the engine did not commit, for example when it rolled the transaction back because a statement had failed; SQL retries a rejected commit only when `isRetryable` accepts its error, so reject with a non-retryable error in that case. `isRetryable` and `normalizeError` receive any object thrown in an owned transaction or operation, application errors included, and never `null` or a primitive; `normalizeError` never receives a `SimfinityError`. `normalizeError` must map its own engine's errors and return every other error unchanged. A failed `acquire`, `begin`, `query` or `commit` that it returns unchanged becomes `DATABASE_ERROR` (500), with the driver error as its non-enumerable `cause` and `getCause()`. `session.query()` rejects with the driver's own error, so a savepoint can recover from it. Value codecs supply `createId()`, `castId(value)`, `encodeScalar(field, value)`, `decodeScalar(field, value, gqlField?)`, and `encodeEmbedded(value)`.

Physical descriptions must preserve the table names, primary keys, column names, presence markers, and ownership metadata needed for record reconstruction. Plugins may extend those shapes with native types, functions, triggers, and other engine metadata. `compileRecord` receives a physical **table object**, with one of these operation shapes:

| `kind` | Additional fields |
| --- | --- |
| `selectById` | `table`, `id`, optional `lock` |
| `selectOwned` | `table`, `ids`, `ordered` |
| `insert` | `table`, `data` |
| `update` | `table`, `id`, `data` |
| `deleteById` | `table`, `id` |
| `deleteOwned` | `table`, `ownerId` |

`planRelationalSchema` indexes single `ID` columns but not `[ID]` lists. Compiled SQL must not depend on the physical column order of a table.

Every runtime requires `transactions`. Planning adds `foreignKeys`, `deferredForeignKeys`, `embeddedValues`, `ownedRecords`, `scalarLists`, `uniqueValues`, and `nullableUnique` when the model needs those guarantees. The optional `singleStatementReads` is never required: a plugin advertises it when one statement reads one consistent snapshot without a transaction and `rollback` resolves on a connection with no open transaction, and sessionless reads of types without owned tables then run on one connection without `begin` and `commit`. To keep a transaction around every PostgreSQL read, pass `createSQL()` a copy of `postgresPlugin(options)` whose `capabilities` leave it out, such as `{ ...plugin, capabilities: plugin.capabilities.filter((name) => name !== 'singleStatementReads') }`. Batched collection reads are opt-in: with `batchedCollections: true` in the configuration and a `compileChildrenQuery`, the adapter reads the generated collection fields of many parents with one statement per 100 parents, one after another, on the connection or transaction `findChildren` would use; when a statement has `setup`, the whole batch, owned-row hydration included, runs in one transaction from `begin` to `commit`, because settings such as PostgreSQL's `SET LOCAL` last only until the end of a transaction. Without `batchedCollections: true`, the adapter has no `findChildrenBatch` and keeps one `compileQuery` statement per field, as 3.6.0 did. A `setup` that is not a list of statements fails the batch with a `TypeError` before a connection is taken, and the runtime reports it once and reads each parent with `compileQuery`. The compiler carries, as its `compileQuery` property, the `compileQuery` whose rows it reproduces, and is bound only when that is the plugin's own: a copy that overrides `compileQuery`, such as `{ ...postgresPlugin(options), compileQuery }`, reads each parent with its override. Embedded/owned capabilities include presence and shape enforcement. Unsupported guarantees fail before physical schema compilation or initialization; a plugin must not silently omit constraints.

`queryFeatures` is `{ operators, referenceEmptiness, quantifiers }`: `operators` lists the `QLOperator` values that `compileQuery` and `compileChildrenQuery` compile, including `EQ`, which a condition without an operator means, and the optional `referenceEmptiness: true` says that they compile emptiness through references and collections, described below. Names Simfinity does not know are ignored. The SQL runtime declares it as its adapter's `queryFeatures` and passes these flags to `createQueryPlan`, so the runtime, before middleware and again before the adapter call, and the plans of reads that do not go through it, such as `model.find()`, reject any other operator with `UNSUPPORTED_QUERY` (400) before `compileQuery` sees it. A plugin without `queryFeatures`, or with `null`, compiles the operators of 3.7.0: `EQ`, `NE`, `LT`, `LTE`, `GT`, `GTE`, `BTW`, `IN`, `NIN` and `LIKE`. A declaration may also name, as `queryFeatures.compileQuery`, the `compileQuery` it describes, and then holds only while that is the plugin's own `compileQuery`; without that member it describes whichever `compileQuery` the plugin has. `postgresPlugin()` declares every operator, `referenceEmptiness: true` and `quantifiers: true`, and names its `compileQuery`, so a copy such as `{ ...postgresPlugin(options), compileQuery: myCompileQuery }`, like `{ ...postgresPlugin(options), queryFeatures: undefined }`, rejects `ILIKE`, `STARTS_WITH`, `ISTARTS_WITH`, `ENDS_WITH`, `IENDS_WITH`, `IEQ`, `IS_EMPTY` and `IS_NOT_EMPTY`, and emptiness through references and collections, until it declares what `myCompileQuery` compiles. `referenceEmptiness` follows the same rule as `operators`, and the adapter's bound `queryFeatures` holds it only when it is `true`; `false`, `null` and an omitted flag mean that the plugin does not compile it.

A plugin that declares `IS_EMPTY` and `IS_NOT_EMPTY` receives their plan predicates as `{ kind: 'predicate', path, operator, value: null }`, after `createQueryPlan` has checked them. Their `path` may end at an embedded object, an embedded list or a scalar list as well as at a scalar, so a compiler must not read it as a value path: it tests the emptiness of the record's own field, as the queries guide defines it, and builds `IS_NOT_EMPTY` as its exact complement, so that every record matches exactly one of the two. A term or group condition written without a `path` arrives with the path of its field. Unless the plugin also declares `referenceEmptiness: true`, the plans reject emptiness through references and collections with `UNSUPPORTED_QUERY` (400).

With `referenceEmptiness: true`, an emptiness predicate's `path` may also cross single references and end at a reference or a collection, and an embedded object may have reference and collection members. A predicate without `scopes` comes from trusted code, such as middleware, scopes and `model.find()` calls, and reads stored data: a reference is empty when it points to no record, a collection when no child points to the record, and a leaf through a reference reads that record's value, as through the joins of other conditions. A predicate with `scopes` is a client's condition, whose marker the runtime filled with the targets' `find` scopes: `scopes` has one key per dotted path from the queried record, for each single reference the path crosses, and for the end and each member that is a reference or a collection, and each value is a predicate planned on that target, or `null` when its scope added nothing. The compiler must read a crossed reference only where its scope admits the target, so that a hidden record reads as a missing one, keep every later hop on that restricted record even when its own scope is `null`, and keep a referenced or child record only where its scope admits it. A `scopes` without a key for one of those paths is an error, never a reason to read the predicate as trusted. While every value on the path so far is `null`, the predicate may compile exactly as a trusted one and share its plain joins. `postgresPlugin()` crosses references through the plain `LEFT JOIN` of other paths until the first value that is not `null`, and from there on through `LEFT JOIN LATERAL (... LIMIT 1)`; it compiles collection ends and members as `NOT EXISTS`, with the scope when it is not `null`, and reference ends and members as `NOT EXISTS` with the scope, or, when their value is `null`, as `"ref" IS NULL`, like a trusted reference; and it fails a predicate whose `scopes` are incomplete with `DETACHED_CLIENT_FILTER` (500).

With `quantifiers: true`, collection filter terms become one correlated `ANY` frame per collection prefix in each filter group. Explicit `ANY`, `NONE` and `ALL` groups and a relation filter's `quantifier` support collections and single references; a missing reference contributes no element, `NONE` rejects matching visible elements, and `ALL` requires every visible element to match under the usual two-valued condition semantics (a null operand fails an ordering condition), with both true on an empty set. The compiler receives `{ kind: 'quantified', quantifier, path, where, scope, joins?, anchor? }`: `path` and the body's paths are relative to their containing frame, `where: null` means no conditions, `scope` restricts visible elements, and `joins` supplies the target predicates for each crossed reference. An aggregate's `anchor` follows the legacy joins that its groupId or facts need and shares those aliases; it never accompanies `joins`. Missing or malformed scope keys must fail with `DETACHED_CLIENT_FILTER` (500). A reference reached through an embedded list with a null target scope retains every vector target and the restricted base of any earlier scoped prefix; a non-null target scope there is forbidden. The flag uses the same compiler identity rule as the other query features and requires `referenceEmptiness: true`; a plugin without it retains collection join semantics and rejects explicit quantified forms. Every plugin rejects sorting through a collection, including count mode.

Invalid plugin structure, including a `compileRecordBatch` or `compileChildrenQuery` that is not a function, a `maxRecordBatchValues` that is not a positive safe integer or a `queryFeatures` that is not an object whose `operators` is an array of strings, whose `compileQuery` is present and not a function, or whose `referenceEmptiness` or `quantifiers` is present and neither a boolean nor `null`, or that declares `quantifiers: true` without `referenceEmptiness: true`, raises `INVALID_SQL_PLUGIN`; unsupported contract versions raise `UNSUPPORTED_SQL_PLUGIN_VERSION`; missing required guarantees raise `UNSUPPORTED_SQL_CAPABILITY`.

`compileQuery` receives `SQLModelDescription`, which extends core model metadata with recursive `SQLFieldDescription` fields. The `state` field of a type with a state machine has `stateNames: [{ value, name }]`: `value` is the string form of the stored enum value, and `name` is its GraphQL enum name. Compilers can use this mapping for aggregate state names. SQL runtimes require the `state` field of a state machine to be a GraphQL enum and reject any other with `INVALID_MODEL` (400) at `createSchema()`. Scalar codecs and `aggregateFields` use the same enriched field type.

TypeScript declarations export `SQLPlugin`, `SQLDriver`, `SQLValueCodec`, `RelationalPlan`, discriminated `RelationalCheck` and `SQLRecordOperation` unions, `SQLInsertManyOperation`, `SQLChildrenStatement`, `SQLChildrenQueryCompiler`, physical storage interfaces, and `SQLRuntime`, `SQLSession`, and `SQLModel`. Plugin generics preserve configuration, native client, physical description, query-result, and ID types through `createSQL`. Application-defined row values use `unknown` until narrowed. The `./internal/adapter`, `./internal/records` and `./internal/transactions` subpaths are deprecated: they are not plugin-author APIs, have no type declarations, are no longer used by Simfinity's packages, and will be removed in 4.0.

A plugin declaring `optimisticConcurrency` must encode valid safe integer versions and decode valid stored `Version` values to numbers. The `update` and `deleteById` operations may include `version: { column, expected }`. A versioned update must atomically match both ID and version, increment the version, and return the updated row, including when `data` is empty. A versioned delete must match both and return a deleted row. Record updates diagnose a returned version other than `expected + 1` as `DATABASE_ERROR`; deletes take a locked read and diagnose a missing returned row as `DATABASE_ERROR`. These checks help catch faulty compiler overrides but do not prove an arbitrary compiler honored the atomic predicate. Copies that override `compileRecord` must preserve these semantics or delegate the two operations to the original compiler. Operations without `version` retain their existing contract.

Controller `onSaveCommitted`, `onUpdateCommitted`, `onDeleteCommitted` and `onTransitionCommitted` callbacks run serially after the owning transaction confirms commit and attempts cleanup. `configureAfterCommit({ onError })` configures reporting per runtime; callback failures do not fail the committed write. Borrowed lifecycle writes, such as those inside a registered mutation or `withTransaction(null, callback)`, join that owner's queue; a session this runtime did not create is rejected with `INVALID_SESSION`, as before. Existing hooks remain transactional. See [the contract, payloads and outbox requirements](https://simtlix.github.io/simfinity.js/guide/controllers.html#after-commit-callbacks).
